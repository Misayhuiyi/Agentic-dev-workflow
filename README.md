# Agentic Dev Workflow

中文 | [English](README.en.md)

一套可以直接放在项目根目录的 AI 长期开发工作流基座。默认面向 Codex，同时提供通用规则、标准 Skill 目录和其他工具的轻量入口。

它解决的是“怎样持续、有条理地与 AI 开发”，不是替你选择框架或生成一套业务架构。小模块、小项目、已有产品和大型系统都可以采用：流程随**本次改动的风险与复杂度**变化，而不是按项目大小增加步骤。

- 普通对话、知识问答和只读解释：直接回答，涉及项目事实时只查相关文件。
- 简单且明确的低风险改动：由对应生命周期 Skill 指导修改和验证，不自动加载 Superpowers 方法。
- 初始需求的证据不足且影响重要决定：先说明缺口，获准后调研，再由用户逐项审核建议。
- 关键可行性假设缺少当前真实环境证据：按需建议最小 PoC/Spike，在已有授权内验证后再投入高成本实现。
- 业务模块或显著业务流程交付：先约定可观察效果、样本和验收人；技术验证通过后仍须人工效果验收。
- 复杂或有未决选择的工作：先明确设计，再用一份计划分阶段推进。
- 换会话或换 Agent：从项目文档、任务状态和真实工作区恢复，不依赖聊天记忆。
- 根目录散乱：先分类并给出移动方案，获准后整理目录、更新引用和验证。
- 控制上下文：长期规则保持简短，Skill 正文和详细参考只在需要时读取。

当前模板版本：`2.3.0`。包含 **11 个项目生命周期 Skill + 14 个 Superpowers 方法 Skill，共 25 个 Skills**，提供 27 个受管适配入口；没有示例业务代码、验收样例项目或构建历史。可行性实验和人工业务验收复用 `project-verification`，不新增 Skill。

## 1. 三分钟开始

### 新项目

1. 在 GitHub 点击 **Use this template** 创建自己的仓库；也可以下载 ZIP，把解压后的内容（包括隐藏目录）复制到空项目根目录。
2. 从这个根目录打开 Codex 或其他具备项目文件访问能力的 AI 编程工具。
3. 发送下面的请求，替换方括号内容：

```text
先读取 AGENTS.md，按需使用项目内 Skills。
我要开发：[目标和面向的用户]。
第一个可验收结果：[一条可以实际演示的业务闭环]。
业务效果与验收：[代表性脱敏样本、可观察的预期结果、验收人；未知时先问清楚]。
约束：[技术栈、运行环境、数据权限、时间等；未知项先只读核对，需外部调研时说明缺口]。
请使用 project-kickoff 开始，先明确边界，不要铺设尚不需要的基础设施。
```

初次使用可先让 Agent 只读确认：项目规则在哪里、能否发现本地 25 个 Skills、有没有同名全局 Skill 或更高层规则冲突。**发现名称不等于已经执行或验证过 Skill。**

建项先只读检查已有材料。如果项目还在初始文档阶段或需求证据薄弱，且缺口会影响目标、可行性或重要设计，Agent 会先说明缺口并询问是否调研。没有 `docs/research/` 目录本身不是触发条件；已有材料足够、明确小任务和普通聊天不需要增加调研步骤。你已明确要求调研时，无需再次批准同一范围；拒绝或尚未回答时，不外部浏览、不擅写调研文件。

### 已有项目

不要直接覆盖现有项目。先在独立目录查看模板，再让 Agent 比较并合并 `AGENTS.md`、同名 Skills、工具入口和文档约定。已有合理路径、业务 README、测试体系和项目许可证优先保留。

```text
将这套工作流接入现有项目。先只读盘点，列出规则/Skills/文档冲突和最小合并方案。
保留现有实现、README、目录约定和未提交修改；未经确认不要覆盖同名文件。
```

不需要同时安装所有 AI 工具，也不需要为使用 Markdown 规则而安装 Python。只有下面的可选辅助脚本需要 Python。

## 2. 目录结构与作用

```text
项目根目录/
├── README.md                    中文使用说明；建项后改为你的业务项目首页
├── README.en.md                 英文使用说明
├── AGENTS.md                    唯一的基础规则与任务路由入口
├── CLAUDE.md                    Claude 的轻量规则入口
├── GEMINI.md                    Gemini 的轻量规则入口
├── .gitignore                   缓存、临时文件和常见本地环境文件的忽略规则
├── .gitattributes               跨平台文本及工作流指纹的 Git 处理约定
├── .agents/skills/              25 个完整 Skill 的唯一正本
│   └── <skill-name>/
│       ├── SKILL.md             触发条件和必要步骤
│       └── references/…         仅部分 Skill 需要的详细参考或辅助资源
├── .claude/skills/              转发到正本的轻量 Skill 入口，不维护第二套正文
├── .ai-workflow/
│   ├── ROUTING.md               生命周期与方法 Skill 的选择规则
│   ├── superpowers-compat.md    Superpowers 与本项目权限、轻重流程的衔接
│   ├── references/delivery-loop.md  按需裁剪的阶段合同；不是每任务必读
│   ├── templates/              项目上下文、调研、任务、设计、验证等文档模板
│   │   ├── research-brief.md    需要持久保存调研时使用
│   │   ├── feasibility-check.md 按需记录最小实验的问题、边界和实际证据
│   │   └── business-acceptance.md 记录业务验收标准、演示证据与人工决定
│   ├── scripts/                两个日常辅助命令及三个内部依赖模块
│   ├── third_party/            上游许可、版本、文件校验与补丁记录
│   ├── VERSION                 工作流版本
│   ├── SOURCES.lock.json        锁定的调研和第三方来源
│   ├── ADAPTERS.lock.json       受管适配文件的指纹，防止覆盖人工修改
│   ├── LICENSE                 本工作流原创部分的 MIT 许可
│   ├── LICENSE-SCOPE.md         许可适用范围
│   └── THIRD_PARTY_NOTICES.md   第三方来源声明
└── docs/
    └── README.md                项目文档导航及维护约定
```

没有预建 `src/`、`apps/`、数据库、容器或 CI。它们应由实际业务和技术栈决定。`references/`、`scripts/` 等 Skill 子目录只在确有用途时存在；上游必要资源不是示例业务。

调研、实验和业务验收记录也按实际需要创建，初始包不生成空业务目录。`project-verification/references/` 中的 [feasibility-check.md](.agents/skills/project-verification/references/feasibility-check.md) 和 [business-acceptance.md](.agents/skills/project-verification/references/business-acceptance.md) 提供详细执行约定，模板用于保存实际内容。

部分 Superpowers 可选辅助资源需要 Git、Node.js、Bash 或宿主的多 Agent/浏览器能力；选用时再检查，不要求一次装齐。Bash 脚本不能直接当作 PowerShell 命令运行。缺少能力时使用受支持的串行/人工核对方式，并如实说明未执行部分。

本模板的开发测试、评测脚手架、历史日志和打包记录不随基座复制。**这不意味着业务项目可以不写测试**；功能与修复仍应补充适用测试并执行验证。

## 3. 日常怎么用

通常直接描述需求即可，Agent 根据规则选择入口；不需要背下所有 Skill 名称。支持显式 Skill 选择的工具也可以使用 `$project-development` 等语法，具体选择方式以宿主为准。

| 你要做的事 | 按需入口 |
| --- | --- |
| 普通对话、知识问答、只读解释或状态查询 | 直接回答；需要项目事实时只读相关文件，不自动加载方法 Skill |
| 从零建项、首次接入已有项目 | `project-kickoff` |
| 明确要求或已批准的项目调研、方案证据比较 | `project-research` |
| 功能、重构、普通非生产 Bug、执行已批准计划 | `project-development` |
| 恢复任务、换会话、暂停与交接 | `project-continuity` |
| 整理散乱文件、调整目录结构 | `project-organization` |
| 依赖、运行时、工具链维护 | `project-maintenance` |
| 最小可行性实验、测试与人工业务验收、代码审查、性能/AI/UX 评测 | `project-verification` |
| 安全审查、身份/权限/租户边界 | `project-security` |
| 项目事实、使用说明和文档维护 | `maintaining-project-docs` |
| 发布、迁移与回滚准备 | `project-release` |
| 生产故障或正在发生的安全影响 | `project-incident-response` |

### 按风险选择路线，不按项目大小套流程

先看五件事：需求是否明确、交互是否不确定、技术/数据/集成是否不确定、有没有权限/外部写入/资金/隐私/生产风险、影响范围与恢复成本多大。详细合同见 [ROUTING.md](.ai-workflow/ROUTING.md)。

| 路线 | 典型任务 | 最小做法 |
| --- | --- | --- |
| A 只读 | 问进度、解释代码、知识问答 | 直接回答或只读核对；不推进历史待办 |
| B 清晰小改 | 按钮文案、已定位低风险 Bug | 范围/验收 → 查影响 → 小改 → 回归 → 展示，无需完整 PRD/原型 |
| C 交互未定 | 审核顺序、角色、驳回规则不清 | 澄清后按需预览；优先现有组件，覆盖等待/失败/取消/拒绝/接管 |
| D 后端 | API、数据、检索、性能 | 用契约、样本、测试、日志、性能及恢复证据；不强制 UI |
| E 核心未知 | AI 效果、算法、数据/工具接入未知 | 先验证最危险假设，限定样本、阈值、预算与停止条件 |
| F 高风险 | 自动发布、权限修改、批量删除、迁移 | 明确授权、审计、幂等与补偿，隔离验证后受控执行；一行代码也不豁免 |
| G 生产事故 | 中断、严重退化、数据/安全影响 | 控制影响 → 已授权恢复 → 验证 → 记录 → 复盘 |

可以组合 C + E，但当前只有一个主路由负责范围。原型看懂了不代表技术可行，PoC 成功不代表业务可用；MVP 只是减少范围，不免除基本质量。

### 从问题到长期维护的闭环

大型业务工作按需经过：问题/现状和基线 → 需求与验收 → 产品原型或技术实验 → 继续/调整/缩范围/停止 → 架构/契约与计划 → 小步业务增量 → 测试/Eval 与人工 UAT → 发布准备 → 部署和受控放量 → 运行反馈/业务效果 → 下一轮或退役。这些活动可以裁剪、并行和回退，不是每次从头排队。

安全、测试、AI Eval、监控和恢复准备从设计及各切片介入。需要全局核对时才读 [delivery-loop.md](.ai-workflow/references/delivery-loop.md)；简单任务不加载该表。PRD 可以放进已有 [spec.md](.ai-workflow/templates/spec.md)，不按文件名另造一份需求。

每个里程碑只需在原任务/计划里说明：需求与范围/不做什么、最大未知及验证、可操作产物、验收和预算、依赖/风险/回退、负责人和确认人。近期详细，远期可调整；优先“一条业务能走通”，不是写完所有数据库才做业务。

```text
按现有 spec/plan 执行本轮已批准的 M1。
交付时告诉我：实现了什么、如何运行体验、哪些真实/哪些 Mock、
实际检查及证据、失败与未验证项、需要我确认什么、下一步能否继续。
M1 验收失败时停止依赖它的 M2；独立且已获准的工作可以继续。
```

明确批准多个里程碑后，可以在前置条件满足时连续推进，不逐函数询问。出现业务假设被推翻、验收不通过、实质扩范围、关键依赖不可用、超预算或新高风险操作时，暂停受影响工作并明确决定点。设计/实施批准不等于生产权限，Agent 或 SDD 自行裁决不等于业务接受。

### AI/Agent 项目按需加什么

只有产品本身包含 AI/Agent 行为时才补专项；用 AI 帮忙写普通代码不触发一整套 AI 文档。复用原 spec，按需读 [Agent 合同](.agents/skills/project-development/references/agent-contract.md) 和 [AI 评测](.agents/skills/project-verification/references/ai-evaluation.md)，明确工具输入输出/权限/副作用、上下文和记忆来源、预算/重试/停止/接管，以及模型、Prompt、Skill、工具、知识和配置版本。

分别判断软件测试、AI 质量评测、业务 UAT、上线后的价值。AI 评测固定合法代表样本、开发与独立验收集、专业口径、基线/阈值、随机波动与质量/延迟/成本；LLM 自评不能代替业务专家。影响结果的 Prompt、Skill、工具或知识变化，同样触发相关回归，不只看代码。

合并不等于部署，部署不等于全部用户可用；灰度通常已经在生产，仍需对应权限。代码回滚不能撤销已经发出的通知或执行的业务动作。生产反馈先确认事实、分类、形成改进假设、测试/Eval，再经审批发布，不直接自动写入生产规则或长期记忆。[Impact Log](.ai-workflow/templates/iteration.md) 记录真实基线、窗口、样本/口径、结果、审核返工成本、局限和业务确认，不预填收益。

### 一个贯穿示例：服装图片处理要求复用

以下仅为说明性示例，不代表真实公司需求、既有功能或已获批准：

1. 操作顺序不明确：先与使用者确认“选择要求—应用单图—修改—复核”，优先在已有组件中预览；明确标出 Mock，包含取消、失败和人工接管。
2. 核心 AI 能否保留图案未知：另做获准样本的有界 PoC，预先约定效果口径与预算。没有样本授权就说明缺口，不用漂亮界面宣布技术可行。
3. 证据支持继续后：先交付“单张图片到人工确认”的真实闭环，给出候选、体验步骤和证据。未通过核心验收，不推进依赖它的批量处理。
4. 人工接受不等于生产授权：再核对外部写入、灰度人群、观测、幂等/补偿与接管。上线后记录审核时间和返工等真实变化及局限，决定下一轮，而不是先承诺效率提升。

### 先调研，再决定

需要补证据时，顺序是：**只读盘点 → 确认调研范围 → 调研比较 → 用户逐项审核 → 接受项纳入原有设计/计划与验收 → 按原授权继续**。已有明确调研请求就是该范围的授权。调研批准不等于技术选型、实施或外部写入批准；后续动作仍以已有授权为准。

```text
使用 project-research，调研离线文档检索是否适合这个项目。
只比较离线可用性、许可证、维护状态和接入现有 Python 服务的成本。
查官方资料、相关论文和高匹配的 GitHub 项目，给出来源、建议编号与不适用项，先供我审核。
```

调研围绕限定问题比较适配性、维护状态、许可、复用成本和不适用项，不按 stars 排名照抄项目。每条建议使用稳定编号（如 `R-01`）并指向可追溯来源；事实、推断和未验证项分别标明。无法联网时说明限制，不声称已经查阅来源。

审核时可以直接回复：

```text
接受 R-01，拒绝 R-02，R-03 待定。
只把 R-01 纳入现有 spec/plan 和验收条件，保留来源与审核记录；暂不实施。
```

只有接受项可以进入原有的唯一 spec/plan 及验收，拒绝和待定项仍留在调研记录中。小调研可直接用回复中的表格完成；需要持久保存时，按 [research-brief.md](.ai-workflow/templates/research-brief.md) 写入现有约定位置，或按需创建 `docs/research/<topic>.md`。事实入口只留链接，不强制建目录或第二份计划；换会话后也不能把候选建议当作已批准需求。

### 关键假设先做最小实验

Agent 根据风险判断是否需要 PoC/Spike：关键假设缺少当前真实环境证据，且失败会改变方案、造成较大返工或成本时，先提出能够回答该问题的最小实验。资料本身不足时先走 `project-research`；成熟、低风险的复用通常无需 PoC，一次例行测试也不因此升级为实验流程。

```text
使用 project-verification，验证现有离线检索方案能否处理我们已脱敏的代表性文档。
先检查当前证据；若关键假设仍未验证，限定一个最小 PoC。
说明要回答的问题、样本与环境、通过/失败标准、时间/费用上限及停止条件。
在已授权的本地范围内执行；需要外部代码运行、付费服务或更大范围时先明确所需授权。
按实际证据给出通过、失败或证据不足，再说明对原有设计/计划的影响。
```

实验方案或资料推断不能代替真实执行结果。保留环境、样本、操作和证据；失败与证据不足也要如实记录。原型不直接当作生产实现。调研授权不包含运行外部代码或付费调用；已有明确的同范围实验授权不重复询问。需要持久保存时使用 [feasibility-check.md](.ai-workflow/templates/feasibility-check.md)，链接原有任务及唯一设计/计划，不另造一份实施计划。

### 业务模块完成前做人工效果验收

业务模块按“用户能完成什么结果”界定，小模块也要验收；内部微调或文案小改可以不适用，但不能按代码行数豁免业务效果。实现前约定业务目标、代表性脱敏样本、可观察的预期效果与验收人；未知项问清楚，不代填。先做最小端到端演示，尽早发现理解偏差。

```text
实现报销单批量导入模块。先与我确认业务目标、代表性脱敏样本、预期结果和验收人。
先演示一批样本从导入到结果核对的最小闭环，再补齐已约定范围。
技术验证通过后，给出候选版本、操作入口/步骤、预期与实际、证据、限制及待我确认点。
我明确验收前，标记“技术完成，整模块待人工验收”，不要视作整模块完成。
```

人工未回复不等于通过；拒绝或附条件但条件尚未关闭时，保持退回或待确认。人工明确接受前，不自动推进依赖该结果的高成本步骤或发布，独立且已授权的工作可继续。原任务内已获授权的修复可以继续；需求或范围改变仍需确认。相关实现或验收标准变化后，旧验收需复核，但不为每个小函数重新办理整套流程。

用 [business-acceptance.md](.ai-workflow/templates/business-acceptance.md) 按需保存标准、演示证据和人工决定；动态状态仍只放在原任务记录中。技术测试证明已检查的技术行为，人工验收确认业务效果，两者不能互相替代。

### 小改动

```text
给现有函数增加一个可选参数，保留旧调用方式；只改相关实现和测试。
验收条件是：[具体边界行为]。请完成并运行现有验证。
```

目标、验收和边界清楚，且沿用现有模式的低风险局部任务，只走对应的生命周期 Skill，简述做法后实施与验证，不自动加载任何 Superpowers 方法。仍须执行适用的回归测试、查明故障根因，并用当前工作区的新鲜证据支持完成声明；这些基本要求不等于必须读取 TDD、调试或完成验证方法的全文。不强制新建 spec、计划、并行任务或迭代日志。

### 复杂工作

```text
实现批量导入和中断恢复，现有 API 必须兼容。
先查明现有调用方和数据约束，明确未决设计，再维护一份实施计划，分阶段验收。
已批准的决定不要反复询问；实质改变数据或对外契约时再确认。
```

未知故障先定位根因；有证据支持的根因可直接用于已授权修复。只有确有独立任务、稳定边界和宿主支持时才并行。提交、推送、部署、付费服务和破坏性操作需要对应授权，不能由“同意设计”推导出来。

## 4. 散乱目录怎么整理

```text
使用 project-organization 盘点当前项目。
识别散落代码、配置、参考资料、任务书和草稿，先只读给出原路径到目标路径的映射。
说明影响的导入、运行命令和文档链接、验证及回退方式；暂时不要移动文件。
```

确认方案后，再明确批准具体移动范围。Skill 会在执行前复核源文件和目标位置；源文件发生变化、目标已存在、链接越界或消费者不明确时停止，不盲目继续。

它不会按扩展名把所有 `.py` 丢进 `src/`，也不会把草稿当成已批准任务书。运行入口可原位保留；同名文档不覆盖；秘密配置只识别路径、不为归类读取值；未知文件和用户修改保持不动。获准移动代码时，需要同步引用并重新运行适用测试。

## 5. 文档怎样同时服务人和 Agent

详细约定见 [docs/README.md](docs/README.md)。采用项目原有路径；没有约定时再按下表创建，不一次性复制全部模板。

| 文档 | 负责记录什么 | 什么时候需要 |
| --- | --- | --- |
| 业务 README | 项目用途、启动方法、文档入口 | 建项后维护；不要让模板说明永久充当产品首页 |
| `docs/project-context.md` | 当前能力、技术栈、真实命令、模块地图、里程碑、已知限制 | 初次接入及项目级事实变化；保持简短 |
| `docs/tasks/index.md` | 活动任务 ID、负责人、工作树与任务文件指针 | 有需要持续跟踪的活动任务时 |
| `docs/tasks/<ID>.md` | 目标、完成项、技术验证、人工验收状态、风险、下一步 | 跨会话或未完成任务；这是动态状态正本 |
| `docs/research/<topic>.md` | 调研问题、来源、建议编号、接受/拒绝/待定状态及纳入位置 | 已获准且需要持久保存的调研；优先沿用现有路径，小调研可仅在回复中呈现 |
| 现有实验记录位置 + `feasibility-check.md` 模板 | 实验问题、样本/环境、判断标准、资源边界、实际结果与证据 | 关键假设需要最小实验且需留档时；不预建空目录 |
| 现有验收记录位置 + `business-acceptance.md` 模板 | 业务目标、标准、候选版本、演示材料、人工决定与依据 | 业务模块或显著流程交付；记录回链原任务，不复制动态状态 |
| `docs/specs/`、`docs/plans/` | 已批准设计与唯一实施计划 | 需要书面设计或复杂步骤时 |
| `docs/adr/` | 长期架构决定、理由与后继决定 | 重要决策时，不记录普通流水账 |
| `docs/iterations/` | 重要迭代的历史总结、验证和遗留事项 | 有值得保留的迭代结果时 |
| `docs/operations/` | 发布、迁移、回滚、事故的实际记录 | 真实运维需要时 |

已完成的小改可只在回复中说明结果。未完成工作即使很小，暂停或交接前也应在已有写入授权内保存最小状态；只读任务则明确“尚未持久化”。已完成任务退出活动索引，但保留原记录与证据链接。

模板示例中的 `RAG-003`、`src/example.py` 等必须替换为真实标识，不能当作项目已存在的事实。

## 6. 换会话时怎样接着做

结束前：

```text
我要换会话。请更新任务 TEXT-001 的真实状态、验证证据、风险和精确下一步；
保留唯一任务记录与可读快照，不复制完整聊天。
```

新会话：

```text
继续任务 TEXT-001。先按 project-continuity 核对任务文件和实际工作区，
给出目标、已完成、未提交内容、验证、风险、精确下一步，再继续已批准范围。
```

任务文件首行 JSON 是唯一结构化状态；下面的人类可读快照由脚本生成。两者不是两份手工进度。脚本只读，不自动写回：让 Agent 在授权范围内更新标记区，保留人工背景和证据备注。

`2.2.0` 在原任务状态中增加可选的 `human_acceptance`，把人工业务验收与技术验证分开。旧记录缺少该字段仍可读取，但人工状态为 `unknown`，不能据此认定业务已通过。待人工验收时任务保持 `active`；六项快照的“验证”栏同时展示技术和人工状态。

人工接受记录需包含验收人、决定依据、时间，以及独立的候选版本和验收标准指纹。相关代码或标准变化使人工验收证据的新鲜度变为 `stale`；重跑技术测试不会自动刷新人工签字。确实不涉及业务效果的任务可记录 `not_required`，但必须有具体理由，并绑定当前 `criteria_sha256` 才能保持 `fresh`；缺少摘要为 `unknown`，准则变化后为 `stale`。脚本能检查结构与指纹，不能鉴别人类签字真伪，也不能自动判断业务任务是否应免验收。不得伪造验收人身份或同意。具体字段按 [task-state.md](.ai-workflow/templates/task-state.md) 填写。

```powershell
# Windows PowerShell；在业务项目根运行，替换真实任务 ID。
py -3 -B .ai-workflow/scripts/project_status.py --root . --task TEXT-001
py -3 -B .ai-workflow/scripts/project_status.py --root . --task TEXT-001 --format json --require-fresh
py -3 -B .ai-workflow/scripts/project_status.py --root . --task TEXT-001 --require-complete --format json
py -3 -B .ai-workflow/scripts/project_status.py --root . --task TEXT-001 --format markdown
py -3 -B .ai-workflow/scripts/project_status.py --root . --task TEXT-001 --check-view
```

从 JSON 的 `snapshot.human_acceptance.current_criteria_sha256` 取得当前准则摘要，它绑定任务的 `goal`、`acceptance` 和 `scope`。按 [task-state.md](.ai-workflow/templates/task-state.md) 记录：只有真实接受当前候选，或实际确认验收不适用时，才把该摘要写入 `human_acceptance.criteria_sha256`。读取摘要不代表已获得人工同意。

macOS / Linux 使用 `python3 -B` 替换 `py -3 -B`。脚本使用 Python 3.10+ 标准库；`2.0.0` 的实测环境为 Windows / Python 3.11.9，其他系统需在自己的项目验证。

没有任务记录时先按模板建立真实记录，不伪造快照。多任务不按“最新日期”猜选；相关文件改变后，旧验证变为陈旧或未知，不能继续当作通过。`--check-view` 缺失/过期返回 1，结构错误返回 2。没有 Python 可人工核对同样六项，并注明未自动验证。

`--require-fresh` 只检查技术验证的新鲜度，不表示技术检查通过或业务已验收。完整完成检查使用 `--require-complete`：必须同时满足任务 `done`、技术验证 `pass` 且 `fresh`、非空的检查动作 `command` 和结果证据 `evidence`，以及人工验收满足“`accepted` 且 `fresh`”或“有具体理由、绑定当前 `criteria_sha256` 且为 `fresh` 的 `not_required`”。非命令式检查可在 `command` 写实际操作步骤；脚本不替你执行或认证这些记录。条件未满足返回 1，结构错误返回 2。先保留真实待验收状态，获得明确人工结论后再更新；不要为了让检查通过提前标记完成。

`--task <ID>` 从活动索引选择；已完成并移出索引的任务，用明确文件路径读取，不扫描全部历史：

```powershell
py -3 -B .ai-workflow/scripts/project_status.py --root . --task-file docs/tasks/TEXT-001.md --check-view --require-fresh
```

这不是实时监控或永久记忆。可靠接续依赖每次暂停前保存必要事实，以及新会话对代码、配置和证据重新核对。

`2.3.0` 自动恢复只选择当前工作树/分支唯一匹配的活动任务；无匹配不回退到其他分支，已完成任务不自动续接。有 Git 却未登记工作区身份时显式选择任务；`--task` 和 `--task-file` 仍支持主动查询历史。无 Git 时脚本可显示唯一活动记录，但 Agent 仍须核实它与当前工作及既有授权一致。状态 schema 1 保持兼容。

## 7. Skill 为什么是按需加载

`AGENTS.md` 只放长期约束、分级与入口；Skill 名称和描述用于发现；正文在使用时读取；引用文件只展开当前步骤需要的部分。先判断当前请求，再选择需要读取的内容：

| 当前请求 | 加载范围 |
| --- | --- |
| 普通对话、知识问答、只读解释或状态查询 | 不自动进入方法流程；涉及项目事实时只查相关文件 |
| 目标、验收、边界明确，沿用现有模式的低风险局部任务 | 一个对应的生命周期 Skill；不自动加载 Superpowers 方法 |
| 非简单、高风险、多步依赖或复杂未知故障 | 一个生命周期 Skill 负责范围，再按当前阶段读取必要的具体方法 |
| 明确要求使用某个方法 | 使用所指定的方法；只提到名称或询问其含义不算调用请求 |

方法读取与基本质量要求分开：简单任务也要进行适用测试、根因核查与证据验证；发现风险或复杂度升级后，才加入所需方法。新会话本身不触发 Superpowers，也不代表要恢复旧任务。

以下方法保留按需自动发现，适用时由生命周期主路由组合使用：

| 方法 | 用途 |
| --- | --- |
| `brainstorming`、`writing-plans` | 未决设计与复杂实施计划 |
| `test-driven-development`、`systematic-debugging` | 非简单或高风险功能/修复的测试设计，复杂未知故障的系统定位 |
| `verification-before-completion` | 非简单或高风险交付的验证关卡；简单任务在主路由内核对证据 |
| `requesting-code-review`、`receiving-code-review` | 需要深入或独立审查的工作及复杂审查意见 |
| `dispatching-parallel-agents`、`subagent-driven-development`、`executing-plans` | 有必要时编排独立工作或执行既有计划 |
| `using-git-worktrees`、`finishing-a-development-branch` | 需要时隔离工作和处理集成收尾 |
| `writing-skills` | 新建或实质改变 Skill 行为时进行场景验证 |
| `using-superpowers` | 方法选择或集成排错需要时读取的可选指南；不是会话启动入口 |

`2.0.1` 对 14 个方法的触发描述和正文入口加入项目适用边界，并移除 `using-superpowers` 的会话启动、回复前调用及“1% 可能性”强制链。具体补丁见 [PATCHES.md](.ai-workflow/third_party/superpowers/PATCHES.md)。本模板追求减少重复与无关读取，**不承诺固定 token 节省比例**。

项目内方法与全局安装的同名 Superpowers 插件是独立来源。此模板的补丁只作用于 `.agents/skills/` 正本及其适配入口，不会修改全局插件；方法间引用也应继续读取项目正本。当前会话已经注入的 Skill 清单不保证随文件修改即时刷新，更新后应在宿主支持的重新发现或新会话中核对来源。若宿主仍强制加载独立插件，应检查其配置和更高层规则；模板不能承诺跨宿主完全禁止加载。

## 9. 两个辅助脚本

### `project_status.py`：恢复状态

作用和用法见第 6 节。内部依赖 `_taskstate.py`、`_workflowlib.py`；不要只复制入口文件。Git 可选，缺少 Git 不会自动初始化仓库，也不能将“未知未提交状态”说成干净。

### `sync_adapters.py`：维护工具入口

修改规则或内置 Skill 后，先检查生成计划，再决定是否写入。默认 dry-run；人工改动导致冲突时保留原文件，不强制覆盖。

```powershell
py -3 -B .ai-workflow/scripts/sync_adapters.py --root . --json
py -3 -B .ai-workflow/scripts/sync_adapters.py --root . --check --json
py -3 -B .ai-workflow/scripts/sync_adapters.py --root . --apply --json
```

POSIX 同样用 `python3 -B`。内部依赖 `_skillmeta.py`、`_workflowlib.py` 和 `ADAPTERS.lock.json`；适配检查只证明生成文件一致，不证明某款 AI 已成功执行工作流。

添加项目专用 Skill 后，可以使用 `--allow-extra-skills`：只维护内置 25 个 Skill 的入口，保留额外 Skill、代理与其锁记录。额外 Skill 的其他工具入口由项目自己维护，此参数不会自动为它们生成代理。

```powershell
py -3 -B .ai-workflow/scripts/sync_adapters.py --root . --allow-extra-skills --check --json
```

## 10. 定制与升级

- 项目专用 Skill 放在 `.agents/skills/<清晰唯一的名称>/SKILL.md`，写明适用条件；详细资料放引用目录，不把大段手册塞进 `AGENTS.md`。
- 业务代码遵循实际技术栈，不为了模板移动所有目录或更换测试框架。
- 保留一份原始模板版本。升级时比较上游变化，再合并自己的规则和 Skill；不要下载新模板覆盖整个业务根目录。
- 修改 vendored Superpowers 前核对来源和许可，在 `.ai-workflow/third_party/superpowers/PATCHES.md` 留下实际补丁说明，并验证受影响行为。升级版本不等于所有旧行为仍然成立。
- 根目录 README 建项后应介绍你的产品。仍需保留模板用法时，可在既有开发文档中维护必要链接，避免两个相互矛盾的项目首页。
