# 具体候选的发布就绪

检查候选提交/产物、未提交差异及完整范围，不能把 HEAD 当整个 dirty 候选。核对目标环境、已有流水线和明确操作授权。

合并、部署和向用户曝光分别确认；一次批准仅覆盖明示的动作、环境与范围。灰度/试点只要触达真实生产用户或数据，就属于生产操作。沿用已获准的阶段范围，不因分阶段机械重复审批，也不把测试环境或小比例当作豁免。

证据必须对应候选：验收、回归、构建、配置/secret 来源、依赖锁、观测指标、告警和负责者。只记录秘密来源，不打印值。缺少证据写未验证，不以模板或 CI 配置存在代替运行结果。

业务模块核对用户/指定验收人的明确反馈、范围及人类验收候选/准则指纹，和技术检查分开。待人工/退回/过期/缺记录即未满足模块就绪条件；按 task-state 模板执行 --require-complete 只检查记录与新鲜度，仍须人工反馈原始依据，不自动证明线上产物与本地文件相同。真实生产候选/环境另行核对。

停止条件包括候选/环境不清、回归阻塞、迁移恢复未验证、权限/数据/费用超界或错误率超批准阈值。例外需已有具体接受依据，不将一次例外泛化。

需要逐步曝光时，在执行前记录每阶段人群、比例及其分母、候选/开关、观察窗口、质量/安全/延迟/成本阈值、负责者和授权依据；明确晋级、暂停、回退由谁判定。样本不足或窗口未到不能视为通过，扩大范围须在已有授权内。普通一次发布不强制引入灰度平台。

发布后观察关键业务路径与指标，明确窗口；没有后台能力只报告当前窗口，不承诺持续监控。分别记录准备、合并、部署、曝光和运行验证状态；部署成功不能推定已曝光或稳定运行。
