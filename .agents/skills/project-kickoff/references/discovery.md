# 建项发现

## 只读发现

从已有 README/索引和实际文件确定语言、构建、测试、调用方、部署与配置来源。读取必要路径，不扫描密钥或整库历史。无 Git 就记录无 Git，不虚构分支和 SHA。

## 已有项目增量接入

复用模块、文档和流程；已授权接入时只补确有缺口的入口。发现 README、AGENTS 或自定义 Skill 先保留，报告重叠并最小整合，不重新脚手架化。

## 空目录

先明确使用者、当前业务流程/痛点、基线证据、输入输出、业务规则与非目标，再核对数据生命周期、外部系统、许可/数据权限、费用和可观察验收。事实、估算、假设与示例分开，未知基线不代填。

最小里程碑覆盖一条完整业务路径，按纵向切片划分，近期细化、远期保留未知。切片合同包含范围/排除项、待消除的不确定性、可体验产物、验收/预算、依赖/回退、负责人/审核人；已有 spec/plan 直接补必要信息，不生成第二计划。技术栈是待设计选择，不能由空目录推导授权；不初始化 Git 或创建整套基础设施。MVP 仅缩范围，不降低该范围内的质量与授权门槛。

## 初始文档阶段

只有需求草案、任务书或参考资料时，先核对其中的事实、来源和未决选择；没有代码不等于没有调研。若现有证据不足以支撑目标、可行性或重要方案，列明缺口及影响，询问是否开展有界调研；获准才转 project-research。用户已授权调研则复用该授权。缺少 docs/research 目录不是证据缺口；不为材料充分的项目强行再调研。

需要书面合同才复用[spec/PRD 模板](../../../../.ai-workflow/templates/spec.md)，把问题证据、需求/验收 ID、决定、任务和后续候选证据连起来；设计批准仍是预期，不能标为能力已实现。

## 原型与实验的触发

只有交互、流程理解或人机分工的不确定性影响决定时才做产品原型；优先复用已有组件，独立 HTML 确有验证价值时再用。明确真实/Mock 边界，按风险展示等待、失败、取消、拒绝、人工接管；后端、接口或批处理项目不为展示额外造 UI。

技术 PoC 回答“在约定条件下能否做到”，产品原型回答“用户是否理解并能完成流程”；问题独立时可以并行，结果互不替代。代表性真实样本、环境、预算和停止条件在已有授权内明确；无法获得时保留未知，不用 Mock 宣布可行。技术实验交 project-verification，原型沿原设计授权执行。

跨阶段依赖确需核对时按需读[可裁剪交付活动](../../../../.ai-workflow/references/delivery-loop.md)；普通小任务不因此逐阶段审批或补齐整套产物。各阶段按证据给继续/调整/缩范围/停止建议，实际决定与既有授权分别核对。

## 歧义

用户已提供的事实不重复询问。影响架构、外部契约、存量数据或费用的未知须定位后再实施；可逆细节可标假设并继续只读工作。未决重要设计才交 brainstorming，复杂实施计划才交 writing-plans，不另造同义文档；清晰低风险接入留在生命周期 Skill 内完成。

例如“只帮我确定方案”应输出里程碑与待批准设计，磁盘保持不变。
