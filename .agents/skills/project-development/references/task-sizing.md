# 任务分级

按变化和风险而非项目大小、文件数量分级；大项目的小改也可以走最短链。

| 条件 | 必需流程 |
| --- | --- |
| 目标、验收和边界清楚，沿用既有模式的低风险局部变化 | 只在生命周期 Skill 内实施、做适用回归并验证；不自动加载任何 Superpowers 方法，也不强制额外设计审批、spec/plan 或委派 |
| 现有契约明确，但失败原因未知 | 先做有界复现和证据检查；仍不明、反复、跨组件或高风险时才加载 systematic-debugging。证据确认的低风险局部修复留在当前 Skill |
| 产品行为、接口、数据或架构仍有未决选择 | 先 brainstorming 澄清受影响设计；不因需要设计就自动要求书面实施计划 |
| 多步依赖、迁移或跨模块交付 | 复用/建立唯一书面计划，分阶段实施和验收 |

功能与修复补充适用回归，能有效复现缺陷时先观察失败再修复；这些质量要求不依赖读取 TDD 方法全文。非简单或高风险实现才选 test-driven-development，复杂交付才选正式完成验证方法。纯文案/链接调整做内容和链接检查。单行权限、支付或数据变更也可能高风险，不能借“小任务”省掉必要的安全、兼容或回滚验证。明确要求使用某方法时遵守用户选择；普通对话与状态查询不进入开发流程。

已有设计/计划仍适用时复用，不重新审批每个小步骤。超出原批准依据的对外契约、存量数据或需求实质变化先确认；风险升级时停止受影响操作。没有业务边界时返回 kickoff；已有任务的会话状态不明时返回 continuity。

同一任务只保留一份权威计划；本文件只决定是否需要方法，不复制其执行步骤。
