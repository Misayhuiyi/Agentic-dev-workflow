# 人工业务效果验收

技术验证回答“实现是否符合检查”，人工验收回答“实际业务能否使用”。一个业务模块以用户可完成的结果界定，既可是一段接口/批处理，也可是一条界面流程；不能只以文件数或页面数判断。

## 范围和时机

新业务模块或显著业务流程交付必须由用户或其指定验收人检查效果，小模块同样适用。不为每个函数、内部子任务或无业务效果变化的文案/内部微调各开一轮；这些可以明确记 not_required 及具体理由，不能以工期、测试全绿或用户未回复豁免模块。

开发前复用/确认业务目标、使用者、代表性脱敏样本、结果口径、异常路径、可观察通过条件和验收人；缺失时询问，不代业务臆定。先做可操作最小闭环，及早演示纠偏，再投入依赖其效果的后续大块工作；无关且已授权的工作可继续。

## 交给人看什么

技术检查通过后，用[人工验收记录](../../../../.ai-workflow/templates/business-acceptance.md)或原任务中的等价小表提交：

- 精确候选版本/文件指纹、环境和实际可操作入口；没有运行入口时说明限制，不伪造链接或截图。
- 业务场景、样本、操作步骤、可观察预期、Agent 实际观察及对应证据，正常/关键异常均按实际范围列出。
- 未覆盖项、已知限制、成本/体验取舍，以及需要人确认的结果。不把截图、单测或 Agent/另一 Agent 自评当作用户接受。

请用户实际审阅/操作并明确接受或指出不符合项。业务角色不可用时标待人工验收；不擅自联系他人或发起外部审批。不因“继续”“收到”、沉默或设计曾获批准，就推断当前候选已验收。已有具体当前候选的明确验收结论直接复用，不反复索要。

## 状态、反馈与完成

技术 verification 与 human_acceptance 分别记录于原[任务状态](../../../../.ai-workflow/templates/task-state.md)首行；详细证据和审核意见保留原位置，链接即可，不建第二套进度表。

- 技术通过但尚无人确认：state 保持 active，human_acceptance 为 pending，留在活动索引；输出“技术验证通过，业务待人工验收”。
- 不通过或有必须解决的附带条件：changes_requested，记录场景、预期/实际差异及修正范围。原修复授权内处理缺陷；需求实质变化先确认，不降低原门槛掩盖失败。
- 明确接受当前范围与候选：accepted，记录验收人、真实时间、反馈来源及独立候选/准则指纹。部分接受只关闭明确接受范围，未闭合的模块不能整体标 accepted。
- 技术 pass 且 fresh、人工 accepted 且 fresh 才可将模块标 done 并退出活动索引；这仍不是发布权限。

相关代码、配置、数据样本、模型/提示或业务准则改变后，原人工结论可能过期。将权威需求及相关输入纳入 related_paths，保留旧审批证据，复核受影响项；不能在只重跑技术测试时自动改写人工指纹。恢复会话时分别核对技术和人工状态，缺记录不当作通过。

有 Python 时按任务模板运行 --require-complete 核查完成条件；该脚本只检查记录结构与新鲜度，不能鉴别人类身份、确认实际操作或判断 not_required 理由是否真实。Agent 仍需核对人类反馈与真实业务范围。无 Python 时手工逐项核对并如实标未自动检查。
