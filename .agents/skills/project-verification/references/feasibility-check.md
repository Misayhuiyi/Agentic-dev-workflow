# 按需最小可行性实验

用最小证据回答一个影响决定的问题，不先搭完整 MVP，也不把所有不确定性都变成原型任务。

## Agent 如何判断

| 现有情况 | 动作 |
| --- | --- |
| 当前约束下已有可复用、可核对的证据，或只是清晰低风险局部改动 | 跳过专项实验，正常实施及回归 |
| 缺资料、版本说明或相似实现依据，查阅即可回答 | 先按授权查证；确需专项调研交 project-research |
| 关键假设只能实测，且失败会改变方案、对外承诺或造成明显返工/成本 | 提出有界实验，得到所需授权后执行 |
| 用户明确要求实验 | 复用已有范围授权，缺关键条件才询问，不重复审批同一范围 |

说明“要不要做”及依据即可；普通任务不额外生成判断报告。无法获得代表性样本/环境时报告证据缺口，不靠玩具数据宣布适用真实业务。项目规模、框架陌生或没有 PoC 目录都不是单独的触发条件。

## 最小实验合同

在原任务/设计中或使用[实验记录](../../../../.ai-workflow/templates/feasibility-check.md)，确认：

- 一个待证伪假设、影响哪个决定；与已批准业务目标的关系。
- 代表性脱敏输入、环境/候选/配置、已有基线；必要的异常/边界样本。
- 可观察指标和通过/失败标准，事先确定，不看完结果再降低门槛。样本不足时只能给局部结果。
- 时间、调用/费用上限、停止条件及允许写入的隔离位置。研究批准不授权付费、生产操作、上传数据或运行下载代码；已有明确实验授权不重复确认。

仅构造回答问题所需的探针/原型，保持业务实现和无关文件不变。达到标准、失败或耗尽上限就停；扩大范围须确认，不无限试错。只读请求只提出合同，不偷偷落盘或执行。

## 结果与返回

记录实际命令/环境、输入与候选指纹、结果、局限及证据链接；区分通过、失败、证据不足。不能运行则未执行，不伪造数据。AI/性能实验另按实际需要读取 ai-evaluation.md，未固定数据或口径不声称改进。

通过仅支持该样本与条件下的可行性，不等于完整模块可用、人工业务接受或生产就绪。原型标记为实验用途；要保留到正式项目，仍需原实现授权、工程化和适用测试，不能把实验代码自动当成正式功能。

结论回到原唯一 spec/plan：能沿原已批准范围继续的就继续；需改变目标、选型、契约或费用时先审核；失败/证据不足则停止依赖该假设的高成本工作，给最小补证或替代选择。记录决策链接，跨会话动态进度仍留原 task-state。
