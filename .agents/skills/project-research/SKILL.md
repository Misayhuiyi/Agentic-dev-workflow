# 需求调研与可复用方案

把资料转成可审核的决策依据，不把搜索结果直接变成需求或开发承诺。适用于初始文档项目，也适用于已有项目的明确调研任务。

## 进入与授权

- 建项发现缺口时，由 project-kickoff 说明“缺什么、影响哪个决定、建议查什么”，询问是否调研；获准后才进入本 Skill。缺少研究目录、代码或某份模板本身不是触发条件，先复用已有资料。
- 用户明确要求查资料或比较相似项目已是调研授权，不重复询问。只批准检查文档、未回答或拒绝调研时，不自行联网调查；标记受影响未知，继续不依赖它的已授权工作，不反复劝调研。
- 调研授权限定问题、资料/联网范围与期望产出；通常先做能支撑决定的最小调查。付费服务、账号操作、下载运行外部代码、引入依赖或对外发送项目材料不由调研授权涵盖。搜索词去除私有需求和敏感信息。

## 查证与提炼

1. 从真实需求列出待回答的问题、已有证据及影响；缺失约束先澄清或标未知，不用同类产品替用户决定目标。信息已足够则直接综合，无须为凑数量再搜。
2. 按问题检索官方文档、原始论文、标准或 GitHub 高匹配项目，逐步缩小范围。对关键结论查看原文/代码，不把搜索摘要、star 数或项目自述当作能力实测。记录链接、访问日期、相关版本/commit/文件及局限；不能访问时明确未核验，不凭记忆伪造最新结果。
3. 比较需求匹配、实现思路、测试/维护情况、离线/部署/资源约束、依赖与迁移成本。区分可借鉴思想、可引用资料、拟引入组件/代码；后两类核对具体材料的许可、归属和使用条件，未知则不复制或宣称可复用。列出不适合本项目的部分，不整仓搬运。
4. 形成简短审阅清单：建议 ID、结论及证据、适用条件、取舍/风险、建议如何影响设计与验收、待用户决定项。区分已核验事实、推断与待验证假设；保留有意义的不同方案。覆盖关键问题或达到约定边界即停止；剩余缺口说明影响，不无限搜索。

## 审核、纳入与交接

请用户按建议确认接受、拒绝或待定；汇报调研完成不等于全部采纳。只把明确接受项按原文档写入授权纳入唯一 spec/plan，附来源/建议 ID、批准依据、具体任务和可观察验收；未批准项留在调研记录，不混入待执行清单。仍有重要设计选择才转 brainstorming，确有复杂依赖才转 writing-plans，简单工作回原生命周期；不另外生成一条开发流程。

有持久化授权且需要跨会话复用时，采用项目已有位置；无约定时用[调研摘要模板](../../../.ai-workflow/templates/research-brief.md)生成 docs/research/<topic>.md。项目事实入口只留摘要和链接，任务动态状态仍使用既有 task-state。小调研可只在回复中列清单；只读请求不落盘，交接注明尚未持久化。

批准绑定具体建议与适用条件；新证据使已批准结论实质变化时，标记受影响决定并重新审核，不静默改写原批准。调研审核不自动授权实施、提交、推送或部署。

例如：只有需求草案且中文检索方案缺证据，先询问是否比较离线方案；用户同意后给出建议 R1/R2，用户只接受 R1，则计划只纳入 R1，R2 保持待定。
